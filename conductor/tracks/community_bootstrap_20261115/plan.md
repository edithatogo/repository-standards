### Required-check settings: concrete remaining change

The caller supplies the stable check name `community-standards` from GitHub
Actions, observed as app/integration ID `15368`. For each repository, add that
check to the default branch's existing required-check set, preserving all
current checks, code-scanning requirements, strict-update policy and other
protections. For a repository without a branch rule, create a narrowly scoped
default-branch required-status rule. The default branch is `main` for thirteen
targets and `master` for `tutorial_health_gt`.

The addition for a ruleset is:

```json
{"context": "community-standards", "integration_id": 15368}
```

The equivalent addition to classic branch protection's `checks` list is:

```json
{"context": "community-standards", "app_id": 15368}
```

These fragments are additive entries, not replacement settings payloads.
Require an actual successful check on the relevant candidate before enabling
the new requirement. Keep the tutorial pending its licence decision and
observable hosted execution. A passing file audit establishes the stated
presence/structure controls; prose quality, legal suitability and GitHub's
health percentage have their own meanings.

The current GitHub connection can publish commits and merge PRs but offers no
administration mutation for branch protection/rulesets. The available browser
session was signed out when settings access was attempted. Required-status
settings have therefore not been changed. The remaining action needs an
authenticated administration session and a fresh settings readback after the
additive update; repository authorisation is already present in the owner's
request.
