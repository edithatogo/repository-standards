# Prepare and qualify the offline image

This workflow prepares public, source-pinned inputs online, then builds and tests
the scanner without network access. It does not register a self-hosted runner,
qualify an application adapter, approve a release, or claim an air-gapped GitHub
control plane.

## Inputs and trust

`base-images.json` fixes the Linux amd64 Docker Official Images by digest. Its
source URLs record the metadata used to select those immutable manifests.
`Base.Dockerfile` combines the Python 3.15.2 slim Debian 13 image with Node 24
and a source-built Git. The build verifies the pinned Git release archive and
compiles it offline without its HTTP transport. It preserves Git's licence.
Online preparation downloads the three Debian packages pinned by URL, version,
size and SHA-256 in `os-packages.json`, including the fixed zlib package.
The offline base build checks the exact starting dpkg database, installs the
verified packages and checks the resulting versions and `dpkg --audit`.
The build purges the unused `mount` and `libncursesw6` packages with normal
Debian dependency checks. It also removes the two optional Python curses
extensions that link against the removed library.
It copies the updated filesystem, including Debian's installed package database
and notices, into a fresh runtime layer. Global npm and npx are omitted because
the scanner uses the separate reviewed Promptfoo installation.

The scanner/model preparer separately verifies source hashes, committed
dependency locks and their complete supplied-asset inventory. The new image must
pass the actual controls and receive fresh SPDX/Grype evidence. The all-layer
scan is retained, including any superseded base records; a smaller image does
not imply a zero-finding result.

The committed locks and their source/advisory review are bound by exact hashes.
Future candidate locks generated by the metadata-only workflow must be retrieved,
reviewed and committed before the image job can use them. Qualification consumes
the committed approved locks and rejects missing or changed input bytes.

## Execute

Use a clean checkout of the exact policy commit on an isolated Linux x64 host
with Docker, Python 3.15.2, Node 24.22.1, uv 0.13.8, `dpkg-deb` and sufficient
disk space.
The local Docker daemon must enforce cgroup v2 memory, process and CPU limits.
Port 80 on host loopback must be available for the temporary local registry.

```sh
bash security/offline-ai/provision/qualify_hosted.sh \
  /absolute/clean/policy-checkout /absolute/new/output-directory
```

The GitHub-hosted workflow uses a separate worktree for the immutable runtime
policy pin. It rejects a pin missing current source changes, and requires the
calling workflow to match that source byte for byte apart from the single policy
SHA. A generated candidate-lock artifact is preparation evidence only.

A squash merge creates a new receiving source commit. Follow it with a pin-only
PR targeting that commit, which must be an ancestor of the pin change. The
pin-only PR reruns source selection and actual image qualification; do not relax
the ancestor or byte-identity checks. Consumer repinning waits for the qualified
release and the remaining gates below.

All image controls run in fresh containers with no network, a read-only root and
policy mount, UID/GID 65534, zero capabilities, no privilege escalation and
measured finite resource limits. The real GLiNER model tests cannot be skipped.
Raw detector findings and model responses are suppressed.

## Execution evidence and runner provisioning

The artifact records the upstream preparation, complete asset manifest,
dependency lock, base and scanner digests, actual image-control receipt and
SPDX inventory. The candidate image and vendor bundle remain on the job's host.
This workflow does not export or upload their binary contents. Redistributing
the image requires a separate review of all applicable notices and complete
corresponding-source obligations; retaining the two scanner notices alone does
not establish that redistribution is qualified.

After the image controls, `collect_sbom.py` downloads the exact Syft 1.57.1
Linux amd64 archive, verifies its size and SHA256, and extracts only the regular
binary. It executes no installer script. The `sbom/` evidence directory retains
the SPDX 2.3 inventory, version output, explicit configuration and private
receipt. The receipt binds the local Docker image ID and digest, tool/source
identity and evidence hashes. The collector checks the SPDX creator and
described container's name/digest, retains the previous action's squashed-image
scope, and leaves release qualification false. The later Grype scan separately
covers all image layers.

After the image controls and SBOM, the hosted workflow collects Grype advisory
evidence for that exact local Docker digest. The Linux amd64 Grype 0.121.3 archive
is fixed by URL, size and SHA256 in `collect_vulnerabilities.py`; `grype.yaml`
is the explicit scanner configuration. The scan includes all image layers,
including packages removed from later layers. It retains unfixed findings and
internal matcher suppressions without adding severity cutoffs or ignore rules.
Package recognition and advisory coverage remain limited by the scanner and its
database; a zero-match report does not prove the image is vulnerability-free.

The `vulnerability/` evidence directory contains the full JSON report, scanner
version, configuration and database status. Its receipt binds their hashes, the
database bytes and Docker image ID. Download, integrity, image, scanner and
database errors fail collection without logging raw findings. The database must
pass its update, age and integrity checks. Successful collection records
`review_pending: true`, `vulnerability_review_qualified: false` and
`release_qualified: false`; vulnerability disposition remains a separate gate.
The hosted scan requires network access for the pinned tool and current advisory
database, and does not change the network-denied scanner control execution.

The registry listens on loopback only and is removed after the run. To provision
the eventual runner, execute the preparation/build/qualification command above
on the approved Linux x64 host using the exact reviewed policy checkout and
listed preparation tools. Public source acquisition is a separate preparation
phase; the build and scanner controls retain their network denial. Record and
review that host's actual image digest, manifest and qualification receipts
before registering its repository-scoped ephemeral runner. Source-built outputs
are not claimed to be byte-identical across hosts, so a hosted image's digest
does not qualify a new local build. Never register an ordinary workstation or
hosted job under misleading runner labels.

The preparation/build command executes the eight image controls; the workflow's
SPDX and vulnerability steps are separate. Run `collect_sbom.py` and
`collect_vulnerabilities.py` with the approved host's newly built digest, its
evidence directory and separate new working directories for the two tools.
Collect and review both evidence products for that local build. Bind the
inventory, complete report, database provenance and review to that host's actual
image and manifest. Hosted-image advisory evidence cannot qualify different
rebuilt bytes, and none of these steps registers or approves a runner.

`runner_registration_qualified`, `application_adapters_qualified` and
`release_qualified` remain false in hosted evidence. Real runner eligibility,
host network isolation, vulnerability review and applicable application/language
qualification remain separate gates before the consumer pin is changed and its
PR is merged.

## Source acquisition and lock review

This directory separates online acquisition of pinned public assets from offline image construction and real qualification. Preparation never registers a runner or declares an image qualified.

## Dependency review gate

The committed locks have `lock_status: reviewed`. Their exact byte hashes and automated review evidence are bound by `sources.json` and `dependency-review.json`. The review retains all 21 shared Python versions and complete hash sets from the existing privacy lock, verifies the 18 added releases against PyPI metadata, and verifies all 603 unique npm releases against their exact registry versions, archive URLs and SHA512 integrities. No large runtime wheels or models were downloaded during that review.

Four exact npm overrides address the advisories reported for `@hono/node-server`, `basic-ftp`, `glob` and `minimatch`, while retaining Promptfoo 0.125.1. The committed review records each advisory and fixed version. The final `npm audit --omit=dev` reports zero known advisories; `npm ci --dry-run --ignore-scripts --omit=dev` passes. PyPI reports no advisories for the 18 added Python releases. These observations are time-bound source checks; the real dependency installation and offline scanner qualification still have to pass. In particular, the major glob/minimatch overrides remain subject to the real Promptfoo evaluation gate.

For future updates, the separate candidate workflow uses Python 3.15.2, Node 24.22.1 and uv 0.13.8 to resolve public metadata from fixed Python version inputs and the exact Promptfoo package. Torch and PyYAML are deliberately excluded from candidate resolution: the CPU Torch wheel has a separately verified upstream digest, and PyYAML is built using the existing source-pinned privacy builder. Set `lock_status` to `candidate_required` while updating inputs; `prepare_vendor.py` fails before downloads in that state.

Each candidate consists of `requirements.extra.lock`, `promptfoo/package.json`, `promptfoo/package-lock.json` and a receipt. It is explicitly unreviewed and cannot qualify an image. Review exact versions, registry origins, hashes, advisories and retained privacy constraints. Commit the reviewed locks and review evidence, update their SHA256 entries in `sources.json.policy_inputs`, and restore `lock_status: reviewed` in that separate reviewed commit. Automated source review is supported; no second-maintainer approval is introduced.

The workflow uploads the candidate as an ordinary artifact. It also emits only the three fixed public lock paths in ordered `OFFLINE_LOCK_CHUNK` JSON records, followed by `OFFLINE_LOCK_RECEIPT`. Reconstruct each path by index, require exactly the reported number of chunks, and verify both SHA256 and Git blob SHA before creating a Git object. These public metadata records permit recovery if the development workspace is unavailable. Do not promote a partial or hash-mismatched candidate.

## Python 3.15.2 patch review

The offline preparation and runtime now require exactly Python 3.15.2. The
committed Python and npm lock bytes, original resolver inputs and
`dependency-review.json` retain their original Python 3.15.1 observations.
Those observations are historical evidence; this patch does not relabel them as
3.15.2 execution results or resolve new dependency versions.

The shared privacy wheel builder requires Python 3.15.2 and verifies the actual
interpreter before rebuilding the same checksum-pinned sources. Offline
preparation invokes it with an isolated environment created from that interpreter.
Both Presidio wheels use the distinct local version `2.2.366+python315.2` and
`Requires-Python: ==3.15.2`; their scanner code and pinned dependency adjustments
are unchanged. The upstream MIT notice is verified in each built wheel. PyYAML
is rebuilt under the selected interpreter. The source catalog binds the builder,
notice and lock bytes, and the new vendor lock and manifest record the resulting
wheel hashes. The model source catalog remains unchanged.

The existing CPython 3.15 wheel tags permit the same ABI target, but successful
installation, `uv pip check` and actual model/Promptfoo execution on the newly
built image remain required evidence. Source tests and an earlier 3.15.1 image
receipt do not qualify this new image.

Primary advisory review on 2026-11-15 established the following dispositions:

| Finding | Python 3.15.2 disposition | Primary evidence |
| --- | --- | --- |
| CVE-2026-115557, compromised intermediate certificates | Fixed in 3.15.2 | [CPython 3.15.2 security changes](https://docs.python.org/3.15/whatsnew/changelog.html#python-3-15-2-final) |
| CVE-2026-114583, `tarfile.tar_filter` link escape | Fixed in 3.15.2 | [CPython 3.15.2 security changes](https://docs.python.org/3.15/whatsnew/changelog.html#python-3-15-2-final) |
| CVE-2026-116566, null bytes in `socket.getaddrinfo` | Remains affected; the 3.15 backport merged after 3.15.2 | [Backport #160925](https://github.com/python/cpython/pull/160925) |
| CVE-2026-103995, permissive HTTP response framing | Remains affected; the 3.15 backport is not merged | [Backport #159021](https://github.com/python/cpython/pull/159021) |

The two residual findings are retained for image review. The enforced
network-denied runtime constrains their network attack paths. Online acquisition
still uses networking; its fixed HTTPS sources and exact expected content hashes
constrain the retrieved assets. These controls do not establish that the affected
Python implementations are fixed, and no advisory is suppressed.

## Prepare the vendor tree

After committing reviewed locks, run on Linux x64 with Python 3.15.2, Node >=22.22.0, npm and uv 0.13.8 installed:

```sh
python security/offline-ai/provision/prepare_vendor.py \
  --destination /new/path/vendor \
  --receipt /existing/evidence/preparation.json
```

Both output paths must be new. Keep the vendor tree outside the clean policy checkout. The script verifies the committed source catalog, review evidence and policy input hashes, downloads checksum-bound Gitleaks/Opengrep/CPU Torch assets, builds the three existing source-pinned privacy wheels, downloads the exact hash-locked remaining wheel closure, and verifies that closure in an isolated environment. It installs Promptfoo with `npm ci --ignore-scripts --include=optional` against the reviewed lock. Published optional packages supply the libsql SQLite binding and esbuild binary. A silent, bounded check exercises an in-memory database query and TypeScript transform before model preparation, without invoking install scripts or downloading replacement native binaries. Model preparation is delegated to the adjacent `prepare_model.py`, which has its own pinned model sources and receipt.

Only after those stages pass does preparation generate and verify the complete schema-v2 vendor manifest. A private receipt binds source records, policy inputs, model provenance and the resulting manifest. A failed run records the failed stage and unexecuted stages and does not mark the image or runner qualified. Raw third-party process output is suppressed during preparation; the candidate resolver uses only public dependency metadata.

The privacy wheel builder writes into temporary storage. The preparer checks the exact three expected wheel outputs and copies only regular, unaliased wheels into the vendor wheelhouse. It retains uv's known build-only `.gitignore` in temporary storage; the [pinned uv 0.13.8 output-directory implementation](https://github.com/astral-sh/uv/blob/0.13.8/crates/uv-build-commands/src/lib.rs) writes that file with the single byte `*`. A local uv 0.13.6 build of a synthetic dependency-free backend reproduced that output; no scanner or model was involved. Any other unexpected build output is rejected. The schema-v2 verifier continues to require a complete inventory and a flat wheelhouse containing only `.whl` files.

The Gitleaks and Opengrep digests were independently checked against their upstream GitHub release APIs. The CPU Torch digest and metadata digest were checked against the official PyTorch CPU index; this avoids CUDA packages. Promptfoo's package integrity was checked against the npm registry and its release tag resolves to source commit `8569e72ed6cf7737082a6042be8d925e40f9739d`. Exact provenance URLs are retained in `sources.json`. Source-built and exported artifacts are bound by their recorded outputs; byte-identical rebuilds have not been demonstrated.

Continue with the existing offline Docker build and `docker/qualify_image.py`. Successful acquisition or installation does not establish scanner behavior, detector recall, model qualification, measured host isolation or runner eligibility.


## Gitleaks rebuild candidate

The existing upstream candidate workflow has a separate bounded Gitleaks job.
It starts from the exact upstream 8.30.1 source and a checksum-pinned Go 1.27.4
toolchain. The catalog binds the report-permissions patch for CVE-2026-124039
and both versions of the patched Go file. The builder verifies the complete
module closure and disables dependency lookup during compilation. It runs the
existing clean and secret detection fixtures and checks that both new and
pre-existing reports have owner-only permissions. The detection rules are unchanged.

The output contains the fixed public metadata files `go.mod`, `go.sum`,
`modules.json`, `module-closure.json`, `gitleaks-LICENSE.txt` and
`candidate-receipt.json`. The built binary stays temporary. Bounded
`OFFLINE_GITLEAKS_CANDIDATE` JSON envelopes provide indexed, hash-bound recovery
of those same public files when the development workspace is unavailable.

Candidate success is not approval. Review the complete source/toolchain/module
identities and commit the exact lock bytes before connecting a strict reviewed
build to vendor preparation. No candidate output is automatically promoted, and
all image, release and runner qualification flags remain false.

The Innovate hosted canary can explicitly select
`--gitleaks-candidate-evidence-only`. Before staging the local binary, it
requires the scan and report fixtures to pass and the catalog, module-closure
metadata and binary bytes to match `gitleaks-image-candidate.json`. The dependency
artifact records the unchanged module closure. The binary hash binds the
patched cross-build. The canary keeps the binary in its
temporary vendor tree and locally built image; it uploads only the existing
value-free receipts and inventories. The normal preparation path still uses the
pinned upstream release. This evidence-only option does not approve the
candidate, authorize its distribution, or establish a passing image or SAST
scan.
